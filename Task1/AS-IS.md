# AS-IS
## AdScale Architecture
#### Основные проблемы текущей системы
- Монолитная архитектура
- Единая PostgreSQL-инстанция
- Синхронный доступ к БД в hot path аукциона
- Отсутствие кэширования
- Отсутствие очередей и event streaming
- Отсутствие горизонтального масштабирования
- OLTP и аналитика работают на одной БД
- Нет высокой доступности
### Предлагаемый подход
#### Постепенная миграция:
- Стабилизация монолита
- Выделение Auction/Bidding Domain
- Внедрение Event Streaming
- Постепенная декомпозиция сервисов
- Переход к Event-Driven Microservices Architecture

### Основные проблемы
**1. Single Point of Failure**
PostgreSQL является:
* транзакционной БД
* аналитической БД
* финансовой БД
* хранилищем событий

Отказ PostgreSQL приводит к полной недоступности платформы.

**Риск: Критический.**

**2. Синхронное взаимодействие с БД во время аукциона**
###### Bid Request
↓
###### Auction Engine
↓
###### Sync Query PostgreSQL
↓
###### Bid Response
Каждый запрос аукциона зависит от скорости БД.
При росте нагрузки:
* растет queue time
* растут lock wait
* растет latency

Текущее состояние:

P95 = 110-120 ms

SLA = 100 ms

После роста на 20% система гарантированно выйдет за SLA.

**Риск: Критический.**

**3. Отсутствие кэширования**

Для каждого bid request:
* чтение кампаний
* чтение ставок
* чтение таргетинга 

из PostgreSQL.


Следствие:

* лишняя нагрузка на БД

* рост latency

**4. Statistics Service напрямую пишет в БД**

###### Click
↓
###### Statistics Service
↓
###### PostgreSQL
Отсутствует буферизация.

Проблемы:
* конкуренция с Auction Engine
* риск потери событий

**5. Аналитика работает на Production БД**

Analytics Service выполняет тяжелые SQL.

Следствия:
* table scans
* блокировки
* деградация latency аукциона

**6. Невозможность независимого масштабирования**

Все компоненты находятся внутри монолита.

Для масштабирования Auction Engine необходимо масштабировать:
* Dashboard
* Analytics
* Finance

что экономически неэффективно.

**7. Отсутствие отказоустойчивости**

Нет:
* реплик
* очередей
* failover
* автоматического восстановления

##### Bottleneck Analysis
Компонент | Проблема | Критичность |
|----------|----------|----------|
| PostgreSQL    | SPOF  | Критично  |
| Auction Engine    | Sync DB   | Критично  |
| Statistics Service   | Direct Writes   | Критично |
| Analytics Service | Тяжелые запросы к БД | Высокая |
| Deployment | Ручной | Высокая |
|Infrastructure | Единый кластер | Высокая

##### Root Cause Analysis
Основная причина проблем:
Монолит
+
Единая БД
+
Синхронная архитектура

Именно эта комбинация не позволяет масштабироваться дальше 15k RPS.
